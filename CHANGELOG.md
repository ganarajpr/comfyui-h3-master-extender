Workflows saved before the input existed, and API graphs that do not send it, still render with it off, so their cached clips keep their fingerprints. - **Chain memory: opt-in `chain_memory` combo (`off` | `picture` | `context` | `picture + context`, default `off`; after `pass1_steps`, before the `time_gate_json` socket; off leaves every prompt, fingerprint and cache unchanged).** A chained clip only receives the previous clip's motion-context latents and the last-frame identity picture, so when a clip ends on an insert (a clock, a phone, a hand) the next clip forgets who stands where, held hands, wardrobe changes and injuries. Each decoded clip also caches the latest frame of the latest shot that shows the most people (`chain_memory.py`: shot cuts from frame differences, three frames per shot counted with a face detector; the clip's last frame when there is no detector or no face) and how many frames follow that shot.
  - **picture:** the cached frame becomes one extra reference picture in the first free slot (skipped with a warning when all nine are used), and the prompt gains a fixed generic "weak reference" line in `subject_definitions` and a continuity line in `retention_analysis` (a short final paragraph when a section is missing; other text untouched).
  - **context:** the next clip's motion context is taken from before the previous clip's trailing insert: the context latents (pass 1 draft and pass 2) lose `ceil(tail / 17)` cycles of 5 video latent steps from the end and the audio is cut to match, so the clip stays on the 17k+5 grid. Only the context copy is truncated; the clip is kept whole and joined and trimmed exactly as before. Unchanged when nothing follows the shot or fewer than `context_length` + 17 frames would remain.
  - **picture + context:** both. A literal `true` (the earlier boolean input) means `picture`.
  - Costs a face-detection pass per clip and forces the synchronous decode. Clips rendered with it on carry the mode in their pass-1 and clip fingerprints from the second clip on, so changing it re-renders them. Tests: `tests/test_chain_memory.py`.

- **Undistilled pass 1 with real CFG: `accel_mode` options "Base + CFG (undistilled)" and "CFG \u2192 Pika hand-off", plus `pass1_cfg`, `cfg_steps`, `negative_prompt`, `cfg_handoff_steps` (all appended after `handoff_step`, before `clips_in`; every existing mode, default and pass-1 fingerprint unchanged).** Every pass 1 so far was a few-step distilled LoRA at CFG 1, so there was no negative prompt and outputs collapsed toward typical ones; this brings H3's undistilled range back for tests.
  - **Base + CFG (undistilled):** pass 1 runs the base model (SigmaShift only, no turbo LoRA) on a regular `cfg_steps`-step schedule (`turbo_sampler` / `turbo_scheduler`) at guidance `pass1_cfg`. `pass1_cfg` 1.0 is "no guidance": the same positive-only guider as today (ComfyUI skips the unconditional branch at CFG 1), no negative encode, no second forward pass. Defaults: `pass1_cfg` 4.5, `cfg_steps` 24. `turbo_lora` is ignored in this mode; `pdd_nfe` stays the base of pass 2's refine schedule (DMAD, replace, 1 step at `pass2_steps` 4), so pass 2, audio refine, chaining and the caches are untouched. Pass 2 always runs at CFG 1.
  - **CFG \u2192 Pika hand-off:** steps 1..`cfg_handoff_steps` (default 8) of the `cfg_steps` schedule run on the base model with CFG, then the `turbo_lora` (Pika) finishes from the noise level the CFG segment stopped at, on its own `pdd_nfe`-step grid at CFG 1 with no added noise. It reuses the Pika -> Flash machinery: `split_handoff_sigmas(cfg_sigmas, k, pika_grid)` (the Pika grid plays the role of the second expert's grid) and the `Noise_EmptyNoise` continuation in `_sample_euler`. `cfg_handoff_steps` is clamped to `cfg_steps - 1`. The existing `handoff_step` dropdown is not reused: its labels are noise levels measured for Pika's own 6-step grid, which do not describe a 24-step CFG schedule. Needs a `turbo_lora`.
  - **Negative branch carries the same references (decision).** The negative conditioning is a second `MiniMaxH3ReferenceToVideo` encode at the pass-1 size with the same reference pictures / videos / audio and `negative_prompt` as the prompt, and it gets the same motion-context guides as the positive on chained clips. Reasons: H3's reference latents (and the continuation keyframes) ride in the packed sequence, so a batched CFG forward needs both branches to have the same layout (third-party H3 guiders state the same: "layout-matched negative"); and with identical references in both branches CFG = uncond + s x (cond - uncond) amplifies only the text difference, instead of also amplifying "references present vs absent", which would push identity, wardrobe and the previous clip's look to an extreme. An empty `negative_prompt` is therefore "unconditional on the references alone". The negative is not rewritten and not passed through the semantic bridge. It is only built when CFG is above 1.
  - **Cache:** the pass-1 fingerprint gains a `cfg` entry only in these two modes: `[pass1_cfg, cfg_steps, negative_prompt]` (+ `cfg_handoff_steps` in the hand-off). `accel_mode` is already a base key, so a CFG render never reuses a CFG-1 clip of another mode, and two CFG renders differing in guidance, steps, negative text or hand-off point never share one.
  - **Cost:** a CFG step is roughly two forward passes (cond + uncond), and `cfg_steps` 24 is 4x Pika's 6, so expect pass 1 around 8x a Pika pass 1 in Base + CFG; the hand-off costs 2 x `cfg_handoff_steps` + Pika's remaining steps. Feed-forward chunking and the VRAM reclaim are sized for the doubled batch.
  - Panel: engine rows for cfg scale / cfg steps / negative prompt (and the hand-off point + Pika LoRA); `web/widget_migration.js` repairs the four appended widgets in older saved workflows. Metadata engine line shows both modes. Tests: `tests/test_cfg_pass1.py`, `tests/test_widget_migration.mjs`; `test_handoff` / `test_hyperflow_flash` / `test_pass2_overrides` input-order checks now skip the four new inputs.
